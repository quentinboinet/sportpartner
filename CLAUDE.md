# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Tech Stack

**Backend :** Symfony 7.4 (PHP 8.3+), Doctrine ORM 3, form login Symfony (sessions), traductions fr/en  
**Frontend :** Twig + Bootstrap 5 + Stimulus + Chart.js + Leaflet (via Symfony Asset Mapper - aucun bundler Node.js)  
**Infrastructure locale :** Docker Compose - `php` (PHP 8.3-FPM alpine), `nginx` (http://localhost:8080), `mysql` (MySQL 8.0, port 3306 sur 127.0.0.1 seulement), `mailhog` (SMTP 1025, UI http://localhost:8025, sur 127.0.0.1 seulement)  
**Production :** Alwaysdata (PHP 8.3), déployée par GitHub Actions  
**APIs externes :** Strava API v3 (OAuth2 + synchro des activités), Open-Meteo (`api.open-meteo.com` prévisions, `archive.open-meteo.com` historique), Nominatim OpenStreetMap (géocodage inverse, widget météo), tuiles OpenStreetMap (cartes Leaflet). Bootstrap Icons est servi par le site (plus de CDN) ; seules origines externes appelées par le navigateur : voir « En-têtes de sécurité et CSP »

## Development Commands

Commandes à lancer dans les conteneurs Docker :

```bash
docker compose up -d                                            # Démarre les services
docker compose exec php bin/console doctrine:migrations:migrate
```

> Il n'existe **aucune fixture** (`src/DataFixtures/` absent) : `doctrine:fixtures:load` échoue (« Could not find any fixture services to load »).

**Assets (Asset Mapper - pas de npm run dev) :**
```bash
# En dev : les assets sont servis dynamiquement par Symfony, aucune compilation nécessaire
# En prod uniquement :
docker compose exec php bin/console asset-map:compile
```

**Ajouter un package JS :**
```bash
php bin/console importmap:require nom-du-package
```
Exception : FullCalendar est servi depuis des fichiers ESM locaux (`assets/lib/fullcalendar/`). Ne **pas** passer par `importmap:require @fullcalendar/*` (voir le commentaire dans [importmap.php](importmap.php)).

**PHP tooling :**
```bash
php vendor/bin/phpunit            # Tests (suites Unit + Functional)
composer analyse                  # PHPStan niveau 6 sur src/
composer cs-check                 # PHP-CS-Fixer (PSR-12 + Symfony) en dry-run sur src/ et tests/
composer cs-fix                   # Applique PHP-CS-Fixer
```

**Lancer un seul test :**
```bash
php vendor/bin/phpunit tests/Unit/Service/UnitConverterTest.php
php vendor/bin/phpunit --filter testMethodName
```

### Règles qualité
- **PHPStan niveau 6 doit rester à 0 erreur** (imposé par la CI, sans baseline). Ne pas ajouter de baseline, d'`ignoreErrors` ni de `@phpstan-ignore`, et ne pas baisser le niveau.
- Dans un controller protégé, récupérer l'utilisateur avec `#[CurrentUser] User $user` plutôt que `$this->getUser()` (typé `UserInterface|null`).
- PHP-CS-Fixer n'est **pas** imposé par la CI. Ne pas reformater du code que l'on ne modifie pas.
- **Tirets : uniquement le tiret classique `-`.** Jamais de tiret cadratin (U+2014), de tiret demi-cadratin (U+2013) ni de signe moins typographique (U+2212, y compris pour un D- ou une marge négative), nulle part dans le projet : code, commentaires, templates, traductions, doc, messages de commit. Exception : les fichiers tiers dans `vendor/`, `assets/vendor/` et `assets/lib/`. Vérification en bash (ne doit rien renvoyer, indépendant de la locale) : `grep -rn $'\xe2\x80\x94\|\xe2\x80\x93\|\xe2\x88\x92' --exclude-dir={vendor,var,.git,lib} . | grep -v "^./assets/vendor"`

## Architecture

### Frontend (Bootstrap + Stimulus + Asset Mapper)
- **Pas de Node.js / npm / Vite.** Les assets sont gérés par Symfony Asset Mapper.
- L'entrée JS est [assets/app.js](assets/app.js) (JS de Bootstrap, controllers, écouteur global des confirmations `data-confirm`), chargée via `{{ importmap('app', {nonce: csp_nonce()}) }}` dans [templates/base.html.twig](templates/base.html.twig). Les CSS (Bootstrap Icons, `app.css`, Leaflet, puis Bootstrap en dernier) sont liés par `<link href="{{ asset(...) }}">` : **aucun CSS importé depuis le JS** (AssetMapper en ferait un module `data:` refusé par la CSP). Seule exception : la page publique d'un plan partagé (`/p/{token}`, `race/public.html.twig`, autonome) charge l'entrée légère [assets/race_public.js](assets/race_public.js) (`{{ importmap('race_public', {nonce: csp_nonce()}) }}`, déclarée `entrypoint` dans `importmap.php`), qui enregistre elle-même `route-preview` et `race-public` (sans Bootstrap ni les autres controllers).
- Les dépendances JS (Bootstrap, Chart.js, @hotwired/stimulus, Leaflet, FullCalendar, Preact) et le CSS de Bootstrap Icons (polices dans `assets/vendor/bootstrap-icons/font/fonts/`) sont dans [importmap.php](importmap.php). Pas de polyfill es-module-shims (`framework.asset_mapper.importmap_polyfill: false`) : un navigateur sans import maps n'exécute pas le JS (pages et formulaires restent utilisables).
- Les controllers Stimulus sont dans [assets/controllers/](assets/controllers/) et **enregistrés à la main** dans [assets/controllers/index.js](assets/controllers/index.js) (`application.register(...)`). [assets/controllers.json](assets/controllers.json) est vide : un nouveau controller non ajouté à `index.js` ne sera pas chargé.
- Les templates Twig sont dans [templates/](templates/), organisés par domaine.

**Temps de passage : deux implémentations à garder identiques.** `race_splits_controller.js` (`fillAuto()`, `compute()`, `parseDuration()`) reproduit `SplitCalculator::fillAutoFromEfforts()`, `SplitCalculator::compute()` et `DurationFormat::parse()` : mêmes règles, même ordre des opérations flottantes, mêmes arrondis dans le calcul (`floor(x / 10 + 0.5) * 10` pour les temps auto, `floor(x * 100 + 0.5) / 100` pour les allures et vitesses ; pas de `round()` de PHP, dont le résultat a changé en PHP 8.4). Toute modification d'une règle de calcul (répartition, erreurs, barrières) se fait **dans les deux fichiers à la fois**, puis se vérifie : rendu serveur et recalcul JS doivent donner exactement les mêmes cellules. Idem pour les **stratégies d'allure** : formules et coefficients dans l'enum `App\Entity\PacingStrategy` (`multiplier()`, `COEFFICIENTS`, `CONSERVATIVE_UNTIL` ; + `PacingIntensity`), miroir `PACING_COEFFICIENTS` / `pacingMultiplier()` / `pacedEfforts()` dans `race_splits_controller.js` ; poids d'un tronçon = effort × m(x), x = milieu du tronçon / distance de l'arrivée, donc seuls les temps auto bougent (temps fixés et temps visé exacts) ; l'écart d'allure `paceDeviationPct` de `compute()` est un % entier `floor(r * 100 - 100 + 0.5)`. `PacingStrategyTest` relit le fichier JS pour comparer les constantes (garder le format `nom: { light: x, medium: y, strong: z }`).

**Plan nutrition : deux implémentations à garder identiques.** `race_nutrition_calculator.js` (`compute()`, `carryList()`, `status()`, `lineHundredths()`) reproduit `App\Service\Nutrition\RaceNutritionCalculator` : mêmes règles (docblock de la classe), calcul **entier uniquement** (centièmes de gramme, dixièmes de gramme par produit, ml), arrondis par `roundDiv()` (au plus proche, demi vers le haut, `intdiv(2a + b, 2b)` / `Math.floor((2 * a + b) / (2 * b))`, exact tant que a < 4,5e15, garanti par les bornes) et `intdiv` ; jamais de `round()` de PHP ni de `Math.round` dans le calcul. Toute règle se modifie **dans les deux fichiers à la fois**, puis se vérifie : rendu serveur et recalcul JS identiques (E2E), et cas aléatoires PHP contre JS identiques sur PHP 8.3 et 8.4+. `RaceNutritionCalculatorTest` relit le fichier JS pour comparer les constantes (`CAP_PCT`, `STATUS_TOLERANCE_PCT`, `STATUS_MIN_SECONDS`, `FLUID_STEP_ML`, `SIGMA_SCALE`, format `export const NOM = valeur;`).

### Auth & access control
- Form login Symfony (`/login`, `/logout`) géré par [LoginController](src/Controller/Auth/LoginController.php), inscription par `RegisterController`. La déconnexion se fait depuis le menu du compte (bloc utilisateur en bas de la barre latérale et du menu mobile, partial [templates/_sidebar_user.html.twig](templates/_sidebar_user.html.twig) : dropdown Bootstrap vers le haut avec profil, paramètres et `logout_path()`). Le remember-me (7 jours) est configuré mais inactif : le formulaire de connexion n'a pas de champ `_remember_me`.
- **Déconnexion protégée par CSRF** (`logout: enable_csrf: true`) : tout lien de déconnexion passe par `logout_path()` (qui ajoute `_csrf_token`) ; `GET /logout` sans jeton répond 403 et ne déconnecte pas. `AccountController` déconnecte par `Security::logout(false)` (sans jeton, voulu). `SecurityConfigTest` vérifie qu'aucun template n'écrit `/logout` à la main.
- **Pare-feu `dev`** réduit à `^/(_profiler|_wdt)/` : tout le reste (assets compris) passe par le pare-feu `main`.
- Contrôle d'accès par `access_control` dans [config/packages/security.yaml](config/packages/security.yaml) (tout est `ROLE_USER` sauf `/login`, `/register`, `/oauth`, `/reset-password`, `/webhooks`, `/switch-locale/` (choix de la langue, aussi sur la page de connexion) et `/p/` (plans partagés), publics, règles placées avant `^/`) et par `#[IsGranted('ROLE_USER')]` sur les controllers, `StravaController` compris (`/oauth/*` est public dans `access_control` mais le contrôleur exige un utilisateur connecté). Il n'y a **aucun Voter** (`src/Security/Voter/` est vide) ni contrôle par plan.
- **Essais de connexion** : `login_throttling.limiter: App\Security\LoginRateLimiter` (voir « Limiteurs de débit et IP du client »).
- Tokens Strava stockés dans `User` avec expiry ; refresh automatique par `StravaService` avant la synchro.

### Plan partagé (page publique)
`/p/{token}` et `/p/{token}/calendar.ics` (`RacePublicController`) sont accessibles sans compte, par le seul jeton. Règles à garder en modifiant cette page (chacune est testée : `tests/Unit/Service/Share/`, E2E) :
- **Rien de privé** : le template ne reçoit que `PublicPlanBuilder::build()` (liste blanche de scalaires), jamais d'entité. Jamais l'e-mail ou l'identifiant de l'utilisateur, les notes privées (course, repères), les autres scénarios, le nom ou la stratégie du scénario, le lien ou le nom du fichier GPX, le site, les données Strava, ni le statut de la course. Les messages publics des repères (`RaceCheckpoint::publicMessage`) sont distincts des notes. Nutrition (option `showNutrition`, désactivée par défaut) : le plan n'est même pas lu si l'option est coupée ; sinon seulement celui du scénario partagé et seulement aux points d'assistance (ce que les proches donnent et les flasques à remplir : clé du catalogue ou nom d'un produit personnalisé, quantités). Toute nouvelle donnée affichée s'ajoute explicitement au builder et à son test.
- **Même 404** pour un jeton mal formé (sans requête), inconnu, régénéré ou un partage désactivé (`RaceShareRepository::findActiveByToken()`).
- **En-têtes** : `X-Robots-Tag: noindex, nofollow` (+ meta robots), `Referrer-Policy: strict-origin-when-cross-origin` (pas `no-referrer` : les tuiles OSM exigent un Referer ; le jeton du chemin ne sort pas du site), `Cache-Control: no-store, private` (désactiver prend effet aussitôt), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`. `SecurityHeadersSubscriber` y ajoute la CSP et `Permissions-Policy` sans toucher ces en-têtes (et sans lire le jeton de sécurité : `NO_AUTO_CACHE_CONTROL_HEADER` posé par le controller) ; `importmap('race_public', {nonce: csp_nonce()})`.
- **Pas de session** : page autonome (n'étend pas `base.html.twig`), ni `app.user`, ni `app.flashes`, ni `csrf_token()` ; langue par `?lang=fr|en`, sinon `Accept-Language` (fr / en), sinon fr (jamais la session ; `LocaleSwitcher::runWithLocale()`). `LocaleSubscriber` ne lit la session que si elle existe déjà ; en dev, seuls les cookies du profileur (`main_*_profile_token`) apparaissent.
- **Échappement** : Twig autoescape (jamais `|raw`), `textContent` en JS ; les infobulles Leaflet de `route-preview` sont échappées par `esc()`.

### Espace Santé (`/sante`)
- **Exercices fournis = contenu en base**, insérés par `Version20240032_CreateHealth` (constante `EXERCISES`, textes fr ET en écrits pour le projet, tutoiement en français ; vérifiés par `tests/Unit/Migrations/CreateHealthMigrationTest.php` : deux langues, énumérations, bornes, longueurs, tirets interdits). Cette migration est figée une fois en production : **toute mise à jour du contenu = une NOUVELLE migration** (`UPDATE healthExerciseText ... WHERE locale = ? AND exercise_id = (SELECT id FROM healthExercise WHERE slug = ?)`, ou INSERT d'un nouveau slug + ses lignes `fr` et `en`), jamais une modification de `Version20240032`. Les slugs sont stables, jamais réutilisés ni renommés.
- **Pas d'avis médical** : textes prudents (pas de diagnostic ni de promesse de prévention), avertissement `health/_disclaimer.html.twig` sur la bibliothèque, la fiche et le plateau. Aucune vidéo fournie : seulement des liens saisis par l'utilisateur (`VideoUrl`, http(s) seulement, simple lien `target="_blank" rel="noopener noreferrer"`, jamais d'intégration).
- **Activité créée par une séance** : locale (`stravaId` NULL) ; `StravaService::syncUserActivities()` n'insère que des activités Strava nouvelles (dédoublonnage par `stravaId`) et ne modifie ni ne supprime jamais une activité locale. Sport choisi à la fin (« Renfo » / « Autre »), proposé par `HealthActivityMapper::sportSlug()` = `sportFor()` de `health_session_logic.js` (à modifier des deux côtés). Une séance aussi enregistrée sur montre / Strava compterait deux fois : la case « Ajouter à mes activités » l'explique. Supprimer une séance propose de supprimer l'activité (cochée par défaut) ; supprimer l'activité ailleurs remet `healthSession.activity_id` à NULL.
- **Brouillon du plateau en `localStorage`** (pas en base) : instantané, hors ligne, aucune écriture pour un brouillon ; pas partagé entre appareils. La séance en cours est en `sessionStorage` (reprise après rechargement).

### Activités saisies à la main et export CSV
- **Origine sans colonne ni migration** (`ActivitySource`) : `stravaId` renseigné = Strava (lecture seule, sauf matériel et ravitaillement) ; sinon une séance Santé pointe vers l'activité (`healthSession.activity_id`, unique) = séance Santé (gérée depuis l'historique Santé) ; sinon saisie manuelle, seule modifiable et supprimable depuis les activités. Une activité gardée après la suppression de sa séance Santé devient une saisie manuelle. Badge d'origine sur la page d'une activité (toutes) et dans la liste (saisie manuelle et séance Santé seulement, une requête pour la page).
- **Accès** : activité d'un autre utilisateur, Strava ou Santé : 404 en GET, 403 en POST (comme l'espace Santé). Jeton CSRF invalide : rien n'est écrit, formulaire réaffiché avec la saisie (422) ; suppression : retour à l'activité avec un message.
- **Saisie** (`ManualActivityForm`, docblock = référence) : sport de la table `sports` ; nom sur une ligne (255 au plus), vide = « <Sport> du <date> » (`activity_form.default_name`) ; date (à partir du 01/01/2000) et heure locales dans le fuseau IANA du navigateur (champ caché `timezone` ; à défaut celui de l'activité modifiée, puis celui de PHP), stockées en UTC comme Strava ; **départ dans le futur refusé** (5 min de tolérance) : une activité est une séance faite ; temps en mouvement et temps écoulé en **trois champs numériques** (heures 0-48, minutes et secondes 0-59, entiers, vide = 0 ; `fieldset` + légende, erreur sur le groupe ; plus de texte libre « 45:30 », ambigu entre 45 min 30 s et 45 h 30), total de 1 s à 48 h, temps en mouvement obligatoire (au moins un champ > 0), temps écoulé facultatif (trois champs vides = temps en mouvement, sinon au moins égal) ; en modification, les trois champs sont remplis depuis les secondes stockées ; distance en km (virgule ou point, 3 décimales, mètres calculés sans flottant) de 0 exclu à 1000, ignorée pour la renfo ; D+ entier de 0 à 20 000 m, ignoré pour la renfo et la natation ; FC moyenne et max de 30 à 250 bpm, moyenne <= max ; matériel `auto` (matériel par défaut du type rattaché au sport, `StravaService::pickDefaultGear()`, comme la synchro), aucun, ou un matériel non retiré de l'utilisateur (plus celui déjà rattaché) d'un type compatible (`GearType::compatibleWithSportSlug()`). Les champs propres à Strava (tracé, flux, vitesse et cadence moyennes) restent vides : allure et vitesse se calculent avec distance / temps. `Activity` n'a ni notes ni puissance : pas de champ pour elles.
- **Avertissements confirmables** (rien n'est écrit, un seul encadré en tête du formulaire, 200, bouton « Enregistrer quand même » = `confirm_warnings=1` qui passe les deux) :
  - **allure ou vitesse invraisemblable** (`ActivityPlausibilityRule`) : course, trail, marche, randonnée plus lentes que 30:00 /km ou plus rapides que 2:00 /km, vélo au-dessus de 80 km/h (bornes incluses dans le vraisemblable, produits entiers sans arrondi). Avertissement et non erreur : un kilomètre vertical ou une randonnée très raide dépassent réellement 30 min/km ;
  - **doublon probable** (`ActivityDuplicateRule`) : autre activité de l'utilisateur, même sport, départ à 30 min près (bornes incluses, en UTC), l'activité modifiée exclue, avec les activités en cause.
- **Partout** : une saisie manuelle est une ligne d'`activities` comme une autre (liste, calendrier, tableau de bord, objectifs, statistiques, cloche, export). La synchro Strava n'insère que des activités Strava nouvelles (par `stravaId`) et ne modifie ni ne supprime jamais une activité locale. Sans `stravaId`, la page d'une activité n'appelle ni Strava ni la météo (pas de tracé).
- **Export CSV** (`ActivityCsvExporter`, `CsvFormat`) : une ligne par activité, ordre chronologique, colonnes `ActivityCsvExporter::COLUMNS` (date et heure de départ LOCALES, sport traduit, nom, distance km, temps en mouvement et écoulé `h:mm:ss`, D+, allure `h:mm:ss`/km sauf vélo ou vitesse km/h pour le vélo, FC moyenne et max, matériel « marque modèle (surnom) », origine, lien Strava), en-têtes dans la langue de l'utilisateur. **Français : séparateur `;` et virgule décimale ; autres langues : `,` et point décimal ; toujours UTF-8 avec BOM et CRLF** (Excel). `fputcsv` avec échappement vide (guillemets doublés, RFC 4180). Injection de formules : cellule commençant par `=`, `+`, `-`, `@`, tabulation ou retour chariot préfixée d'une apostrophe (OWASP). Réponse en flux (`StreamedResponse`), `Content-Disposition: attachment; filename=sportpartner-activites-<début>_<fin>.csv` (préfixe traduit, `-<sport>` pour la liste filtrée), `Cache-Control: no-store, private`, `X-Content-Type-Options: nosniff`. Bornes comme la vue d'ensemble (heure stockée UTC entre le premier jour 00:00:00 et le dernier 23:59:59) : les lignes correspondent aux totaux affichés, la date écrite est la date locale.

### En-têtes de sécurité et CSP
`App\EventSubscriber\SecurityHeadersSubscriber` (requête principale seulement ; testé par `tests/Unit/EventSubscriber/`, `tests/Unit/Security/`, `tests/Unit/Twig/CspExtensionTest.php`, `tests/Unit/Config/TrustedHostsConfigTest.php` et l'E2E `e2e_secfix_platform.py`) :
- **Requête** : nonce CSP aléatoire (`random_bytes(16)` en base64) dans l'attribut `_csp_nonce`, lu par `csp_nonce()` (`Twig/CspExtension`, toujours le nonce de la requête PRINCIPALE). En prod, requête non HTTPS redirigée vers `https://<hôte><uri>` (301 pour GET / HEAD, 308 sinon), avant la session et le routeur ; HTTPS détecté nativement sur Alwaysdata (pas de `trusted_proxies`).
- **Réponse HTML** (Content-Type `text/html` ou absent) : `Content-Security-Policy` (APPLIQUÉE, pas Report-Only), `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), payment=(), usb=(), geolocation=(self)` (géolocalisation gardée pour le widget météo ; Wake Lock et presse-papiers non restreints). `X-Content-Type-Options: nosniff` sur toutes les réponses. Un en-tête déjà posé par un controller n'est **jamais** remplacé (`RacePublicController`). Page HTML d'un utilisateur connecté : `no-store` + `private` en plus (bouton Retour après une déconnexion sur un ordinateur partagé), sauf si le controller gère son cache (`AbstractSessionListener::NO_AUTO_CACHE_CONTROL_HEADER` : image de la photo de profil, plan partagé). Prod + HTTPS : `Strict-Transport-Security: max-age=31536000` (sans `includeSubDomains` ni `preload`). Dev : rien sur `/_profiler` et `/_wdt` ; la barre de debug ajoute son propre nonce, et l'`ErrorListener` de Symfony retire la CSP des pages d'erreur en debug.
- **CSP** (`App\Security\ContentSecurityPolicy::header()`, chaîne exacte testée) : `default-src 'self'; script-src 'self' 'nonce-<N>'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https://*.tile.openstreetmap.org; font-src 'self' data:; connect-src 'self' https://api.open-meteo.com https://nominatim.openstreetmap.org; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; frame-src 'none'; worker-src 'none'`. Pas de `'strict-dynamic'` : tous les modules sont servis par le site, le CSS de Bootstrap est lié par `<link>` (plus importé par `app.js`, ce qui produisait un module `data:`), et les `<link rel="modulepreload">` d'`importmap()` (sans nonce) passent par `'self'`. `style-src` garde `'unsafe-inline'` (nombreux attributs `style` et blocs `<style>`) : **ne jamais y ajouter de nonce** (il désactiverait `'unsafe-inline'`). `font-src data:` : police d'icônes intégrée au CSS injecté par FullCalendar. `img-src data:` : icônes SVG du CSS de Bootstrap.
- **Script inline** : à éviter (préférer un controller Stimulus) ; sinon `<script nonce="{{ csp_nonce() }}">` (classique ou `type="module"`), y compris dans les pages autonomes (`race/plan_print.html.twig`). `importmap()` reçoit toujours `{nonce: csp_nonce()}`. `base.html.twig` expose le nonce dans `<meta name="csp-nonce">` (FullCalendar le pose sur ses `<style>`). **Interdits** : gestionnaires inline (`onclick=`, `onsubmit=`...), liens `javascript:`, `eval` / `new Function`, `<script src>` ou `<link>` vers un autre site, CSS importé depuis le JS, HTML construit avec des données externes (`innerHTML`) : `textContent` / `setAttribute` / `style.xxx`. `tests/Unit/Security/CspTemplateComplianceTest.php` vérifie tous les templates (nonce sur chaque `<script>`, `importmap()` avec nonce, aucun `on*=` ni `javascript:`, aucune ressource externe, aucun `import '...css'` dans `assets/`). Un script ou un gestionnaire bloqué ne fait rien SANS erreur visible pour l'utilisateur (seulement en console) : vérifier toute page modifiée avec l'E2E (aucune violation CSP).
- **Confirmation avant envoi** : `<form method="post" data-confirm="{{ 'cle.de.traduction'|trans }}">` (jamais `onsubmit="return confirm(...)"`, ignoré par la CSP : la suppression partirait sans confirmation). Un seul écouteur délégué dans `assets/app.js`, en phase de capture : il pose la question avant les actions Stimulus et les écouteurs du formulaire, et un refus annule l'envoi et arrête la propagation. Un controller ne repose jamais la question de `data-confirm` (`race_splits_controller.js` ne pose que ses questions de modifications non enregistrées ; `race_plan_controller.js` n'a plus d'action `confirm`). Pages sans `app.js` (plan partagé, fiche imprimable) : pas de `data-confirm`.
- **Ajouter une origine externe** (nouvelle API appelée par `fetch`, tuiles, image distante) : constante de `ContentSecurityPolicy` (`CONNECT_ORIGINS`, `IMG_ORIGINS`, ou nouvelle directive), en `https://` et la plus précise possible (jamais `https:` ni `*`), puis `ContentSecurityPolicyTest` (chaîne exacte), cette section, et l'E2E. Un script, une feuille de style ou une police tierce : à servir en local (`importmap:require`, ou fichiers vérifiés dans `assets/lib/`), jamais par CDN. Une origine non déclarée échoue en silence côté utilisateur (violation en console).
- **Hôtes de confiance** (prod seulement, `config/packages/framework.yaml`) : `'^%env(regex_quote:key:host:url:APP_URL)%$'`, l'hôte exact d'APP_URL, points échappés par `App\Env\RegexQuoteEnvVarProcessor` ; un autre `Host` = 400. APP_URL sans hôte : erreur au démarrage. Dev et test : aucune restriction (localhost, 127.0.0.1, tous ports des E2E). Un nouveau domaine de prod = changer APP_URL.
- **Cookies** : `framework.session.cookie_secure: true` en prod (le remember-me en hérite), `auto` ailleurs.
- **Journaux de prod** (`config/packages/monolog.yaml`) : fichiers journaliers `var/log/prod-AAAA-MM-JJ.log` et `deprecation-AAAA-MM-JJ.log`, 14 jours gardés ; tampon `fingers_crossed` (vidé à la première erreur, hors 404 / 405) sans les canaux `event`, `doctrine` ni `deprecation`.

### Limiteurs de débit et IP du client
- **Configuration** : [config/packages/rate_limiter.yaml](config/packages/rate_limiter.yaml), stockage = pool de cache par défaut (`cache.rate_limiter`, enfant de `cache.app`, fichiers dans `var/cache/<env>/pools` : un déploiement, qui supprime `var/cache/prod`, remet tout à zéro), sans verrou (`symfony/lock` absent). Réglages vérifiés par `SecurityConfigTest`. Injection par nom : `RateLimiterFactoryInterface $stravaSyncLimiter` (nom du limiteur en camelCase + `Limiter`, jamais la classe `RateLimiterFactory`, alias déprécié). Clé `user-<id>` pour les limiteurs par utilisateur. Délai affiché « réessaie dans N min » par `App\Security\RateLimitRetry::minutes()` (arrondi au-dessus à 5 s près : le limiteur arrondit son échéance à la seconde supérieure).
- **Réglages** : `login` 5 essais / 15 min glissantes (e-mail + IP) ; `registration` 10 / heure glissante (IP, 429 + `Retry-After`) ; `strava_sync` 1 / 5 min ; `strava_gear_import` 1 / 10 min ; `account_delete` 5 / 15 min ; `gpx_import` 10 / 10 min (fichier et lien ensemble) ; `avatar` 10 / 10 min (envoi et photo Strava ensemble). Les endpoints JSON (ravitaillement, nutrition, séance Santé, notifications, météo) n'ont pas de limiteur. Dépassement = message flash et redirection habituelle de l'endpoint (inscription : formulaire réaffiché en 429).
- **Décision : pas de compteur global par IP pour la connexion.** Derrière le proxy d'Alwaysdata, `Request::getClientIp()` renvoie `REMOTE_ADDR`, non vérifié (pas de `framework.trusted_proxies`) : ce peut être l'IP du proxy, partagée par tous les visiteurs. Le limiteur par défaut de `login_throttling` ajoute un compteur global par IP (5 x `max_attempts`) qui, dans ce cas, bloquerait TOUTES les connexions à la fois. `App\Security\LoginRateLimiter` (security.yaml `login_throttling.limiter`, service déclaré dans `services.yaml` avec `@limiter.login` et `%kernel.secret%`) n'applique donc qu'UN compteur, clé HMAC-SHA256 de l'IP + adresse e-mail normalisée (`trim` + minuscules ; ni l'adresse ni l'IP en clair dans le cache) ; une connexion réussie le remet à zéro. Si l'IP est celle du proxy, la limite devient « par adresse e-mail » : un tiers peut bloquer un compte 15 minutes, jamais les autres. Clé et comportement testés par `LoginRateLimiterTest`. Même raison pour l'inscription : limiteur par IP volontairement large.
- **Vérifier l'IP du client en production** (à faire une fois, puis à refaire si l'hébergement change) : déposer temporairement `public/ip-check.php` contenant `<?php header('Content-Type: text/plain'); echo $_SERVER['REMOTE_ADDR'], "\n", $_SERVER['HTTP_X_FORWARDED_FOR'] ?? '-', "\n", $_SERVER['HTTP_X_REAL_IP'] ?? '-';`, l'ouvrir depuis deux réseaux différents (wifi, 4G) et comparer avec l'IP publique affichée par un service comme ifconfig.me, puis **supprimer le fichier**. Si `REMOTE_ADDR` est l'IP réelle : rien à faire (le limiteur est déjà par e-mail + IP réelle). Si c'est une IP du proxy (identique depuis les deux réseaux) et que l'IP réelle est dans `X-Forwarded-For` : déclarer les adresses du proxy d'Alwaysdata dans `framework.trusted_proxies` (`trusted_headers: ['x-forwarded-for', 'x-forwarded-proto']`), jamais `0.0.0.0/0` ni `REMOTE_ADDR` sans vérification ; ensuite seulement, un compteur global par IP pourra être ajouté.
- **Strava** : le retour OAuth et la synchro ne doivent jamais appeler Strava avant leurs contrôles (state, CSRF, limiteur) : `StravaControllerTest` le vérifie avec `MockHttpClient`.

### Webhooks
Aucune route webhook n'existe aujourd'hui, mais `^/webhooks` est déjà en `PUBLIC_ACCESS` dans [security.yaml](config/packages/security.yaml). Si un webhook (ex. Strava) est ajouté, le placer sous `/webhooks` et ne pas le mettre derrière `ROLE_USER`.

## Conventions base de données

### Nommage des tables - camelCase obligatoire

Toute **nouvelle** table utilise le **camelCase** (ex: `athleteProfile`, `raceIntent`). Les tables existantes ne suivent pas toutes cette règle (voir ci-dessous) : ne pas les renommer sans migration.  
MySQL sur Linux (prod) est **sensible à la casse** : `Race` ≠ `race`. En local sous Windows, MySQL ne l'est pas, donc une erreur de casse ne se voit qu'en prod. Sans annotation explicite, Doctrine utilise le nom de la classe PHP comme nom de table (PascalCase), ce qui peut diverger de la migration.

**Règle : toujours déclarer `#[ORM\Table(name: '...')]` sur chaque entité.**

```php
#[ORM\Entity(repositoryClass: RaceRepository::class)]
#[ORM\Table(name: 'race')]          // <-- toujours explicite
class Race { ... }
```

**Checklist à chaque nouvelle entité :**
1. Ajouter `#[ORM\Table(name: 'nomEnCamelCase')]` sur la classe
2. Utiliser le même nom dans le `CREATE TABLE` de la migration
3. Vérifier la cohérence casse migration ↔ entité (Linux ≠ Windows)
4. Donnée rattachée à un utilisateur (directement ou par sa table parente) : clé étrangère `ON DELETE CASCADE` dans le mapping ET la migration (`SET NULL` pour un lien facultatif), sinon la suppression du compte (`AccountDeleter`) échoue ou laisse des lignes ; puis compléter `AccountDeletionCoverageTest` (liste attendue), le docblock d'`AccountDeleter` et le texte de la zone de danger (`account.delete_item_*`)

## Déploiement

**Un push sur `main` part en production.** Le workflow [.github/workflows/deploy.yml](.github/workflows/deploy.yml) :
1. Job `checks` (push et pull request vers `main`, PHP 8.3) : `.env` factice, `composer install`, **`composer audit`** (une faille connue dans `composer.lock` bloque le déploiement), `cache:warmup --env=dev`, PHPUnit, PHPStan, `lint:container`, `lint:twig`, `lint:yaml`, `doctrine:schema:validate --skip-sync`.
2. Job `deploy` (push sur `main` uniquement, si `checks` passe) : en SSH sur Alwaysdata, `git fetch origin main` puis `git merge --ff-only "$DEPLOY_SHA"` (exactement le commit testé, `github.sha` passé par `envs`), `composer install --no-dev`, suppression de `var/cache/prod`, **`doctrine:migrations:migrate` en prod**, `asset-map:compile`, `cache:warmup`.

Workflow : `permissions: contents: read` ; chaque action épinglée sur un SHA complet avec la version en commentaire (mises à jour proposées par Dependabot, [.github/dependabot.yml](.github/dependabot.yml) : `composer` et `github-actions`, chaque semaine ; les paquets d'`importmap.php` se vérifient avec `importmap:outdated` / `importmap:audit`). SSH : mot de passe (`ALWAYSDATA_SSH_PASSWORD`) et, dès que les secrets existent, clé `ALWAYSDATA_SSH_KEY` + empreinte d'hôte `ALWAYSDATA_SSH_FINGERPRINT` (avec `appleboy/ssh-action` v1.0.3, un secret vide est ignoré ; étapes de migration dans le README, « Déploiement »).

Conséquences : ne jamais pousser sur `main` sans accord explicite ; une migration est exécutée en prod dès le push ; `composer.json` et `composer.lock` doivent être commités ensemble.

## Limites actuelles
- Synchro Strava **manuelle** (`POST /strava/sync`, une toutes les 5 minutes) : pas de webhook Strava. Les autorisations accordées au retour OAuth sont signalées mais pas enregistrées.
- Matériel : import Strava manuel (bouton de l'onglet Matériel) et synchrone. Le scope OAuth inclut `profile:read_all` depuis cet import (`StravaService::SCOPE`) : un compte connecté avant doit reconnecter Strava pour que le matériel jamais utilisé soit aussi importé.
- Cloche « À faire » : liste calculée à la demande, ni e-mail ni notification push ; les éléments masqués sont gardés dans le navigateur (`localStorage`, par compte), pas en base. Le scope Strava accordé n'étant pas enregistré, un compte sans `profile:read_all` n'est pas signalé.
- Pas de paiement : aucun Stripe/billing. Les colonnes Stripe de `User` et `subscriptionPlan`/`isPro()` ne servent qu'à afficher un libellé (Pro/Amateur).
- Pas de vérification d'email ni de « mot de passe oublié » (la règle `^/reset-password` n'a aucune route).
- Limiteurs de débit en place (connexion, inscription, suppression du compte, synchro et import Strava, GPX, photo), mais l'IP réelle du client n'est pas confirmée en production : connexion limitée par e-mail + IP sans compteur global par IP, donc 5 erreurs de mot de passe d'un tiers bloquent un compte 15 minutes (voir « Limiteurs de débit et IP du client », à vérifier puis `trusted_proxies`). Limiteurs remis à zéro à chaque déploiement (cache supprimé). Suppression du compte immédiate, sans délai de grâce ; le retrait de l'accès Strava est au mieux : s'il échoue, l'application reste listée dans « Mes applications » de Strava (les jetons sont effacés avec le compte, un message invite l'utilisateur à la retirer).
- Pas de fixtures ; tests unitaires seulement (`tests/Unit/`), aucun test fonctionnel.
- Plan de course : phases 1 (GPX + repères) et 2 (scénarios, temps de passage, stratégies d'allure, fiche imprimable / bracelet) faites, ainsi que le lien de partage public pour les proches (horaires PRÉVUS seulement : aucun suivi en direct) et le plan nutrition par scénario (auto + ajustements, liste à emporter, fiche, bracelet, option du partage). Le plan nutrition suit les temps de passage ENREGISTRÉS : modifier les temps sans enregistrer le scénario ne change pas les durées des tronçons. Restent la phase 3 (modèle d'allure auto tiré de l'historique, à brancher sur `SplitCalculator::segmentEfforts()`) et la phase 4 (comparaison après course).
- Upload GPX en local : `upload_max_filesize` de WAMP souvent à 2M (Docker : 20M).
- Photo de profil : la limite affichée est min(5 Mo, `upload_max_filesize`, `post_max_size`), donc 2 Mo sous WAMP. En prod, il faut GD avec le WebP (sinon sortie JPEG) et l'extension `exif` (sinon l'orientation des photos de téléphone n'est pas corrigée).
- Espace Santé : pas de programmes tout faits (séances composées à la volée), plateau non partagé entre appareils, aucune vidéo fournie ; l'activité créée par une séance n'a ni distance, ni FC, ni calories mesurées.
- Saisie manuelle : pas de notes ni de puissance (absentes d'`Activity`), pas de tracé GPS ni de fichier importé (GPX / FIT), pas de saisie depuis le calendrier ; doublon probable et allure invraisemblable ne sont que des avertissements. Export CSV seulement (pas d'Excel, de GPX ni d'import).
- Le schéma de la base locale diverge déjà du mapping Doctrine (index, types de colonnes) : vérifier `doctrine:schema:update --dump-sql` avant d'écrire une migration.
